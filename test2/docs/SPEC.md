# Спецификация MVP v0.2

## Цель и архитектура

Сквозной сценарий образовательного хакатона: описание бизнес-задачи → уточнение →
редактируемая карточка → ручное подтверждение → публикация → предложения команд →
ручное решение бизнеса. React + Vite frontend реализует этот сценарий через API.

Стек сохраняется: FastAPI, синхронный SQLAlchemy 2, SQLite, одна сессия на запрос.
Директории `backend/`, `database/`, `frontend/`, `docs/` не меняются.
В `backend/app/ai/` добавлен изолированный анализ текста; отдельного сервиса нет.

## Сценарий

1. `POST /api/tasks`: короткое description (1–2000 символов), необязательная topic.
   AI-слой анализирует описание и создаёт draft с десятью полями карточки.
2. `GET .../questions`: недостающие поля и три различных уточняющих вопроса.
   Незаполненные поля имеют приоритет; если их меньше трёх, вопросы дополняются
   уточнениями по заполненным полям. Тексты вопросов нейтральные, из шаблонов.
3. `POST .../answers`: минимум три ответа на разные поля. Ответы напрямую
   переносятся в structured card; AI не вправе их изменять. Пустой ответ допустим.
4. `PATCH /api/tasks/{id}`: частичное редактирование карточки и темы.
5. После создания, ответов и каждого редактирования рейтинг рассчитывается сразу.
6. `POST .../confirm`: бизнес вручную подтверждает карточку; требуется минимум
   три сохранённых ответа, включая явно пустые. Подтверждение не зависит от рейтинга.
7. `POST .../publish`: подтверждённая задача появляется в каталоге при любом балле.
8. Команда отправляет идею, план, оценку длительности и необязательную ссылку прототипа.
9. Бизнес вручную принимает либо отклоняет предложение. Автоназначения команды нет.

## Модели

Task содержит:

- `id`, неизменяемое `description`, `topic` (до 100 символов, trim + casefold);
- `title` (до 200), `context`, `need`, `users`, `data_materials`, `constraints`,
  `expected_result`, `success_criteria`, `contact`, `interaction_format`
  (остальные поля до 10 000 символов каждое);
- JSON `answers` — исходные ответы, отдельно от текущей карточки;
- JSON `ai_analysis` — provider, fallback_reason, question_fields;
- `status`, `readiness_score`, `readiness_level`, JSON `score_breakdown`;
- UTC `created_at`, `updated_at`, nullable `confirmed_at`, `published_at`.

Карточка хранится плоско в Task. Поля карточки — строки; неизвестное = пустая строка,
не null. Поле `rating` в ответе вычисляется из текущей карточки; рейтинг и уровень
также сохраняются в БД для сортировки и фильтрации каталога.

Proposal содержит `id`, FK `task_id`, `team_name`, `solution_idea`, `plan`,
`estimated_duration`, `prototype_url`, необязательный `contact`, `status`,
`created_at`, `decided_at`. Старый `message` сохранён как совместимый дубль
solution_idea. Новые предложения требуют непустые team_name, solution_idea, plan,
estimated_duration. Prototype URL может быть пустым, иначе только HTTP(S).
Длительность — свободный текст, например «5 часов».

TeamProfile — минимальный демонстрационный справочник: id, уникальное name,
description, JSON-массив skills, contact. Пять профилей загружаются seed и доступны
через GET /api/teams (limit/offset). Это не аккаунты: регистрации и привязки
авторизации нет. Proposal по-прежнему хранит свободные team_name/contact;
профили ничего не назначают автоматически. Новая отдельная таблица создаётся
идемпотентно при startup/seed, существующие Task/Proposal не меняются.

## Состояния и решения

- Задача: draft → confirmed → published.
- Редактирование карточки/темы или ответов сбрасывает подтверждение, возвращает draft,
  сразу пересчитывает рейтинг. История ответов остаётся.
- Опубликованные задачи пока нельзя редактировать или снимать с публикации.
- Повторные confirm/publish безопасны, timestamps не меняются.
- `status=draft` — состояние процесса, `rating.level=draft` — уровень готовности.
- Предложение: pending → accepted или pending → rejected, только вручную.
- Окончательное решение нельзя сменить; повтор того же решения допустим.
- Максимум одна accepted-команда на задачу: уникальный частичный SQLite-индекс.
  Условное обновление pending защищает окончательное решение от перезаписи.
- Другие предложения остаются pending до ручного решения. Новые отклики после
  выбора команды разрешены; автоматического закрытия набора нет.

## Рейтинг

Оценивается заполненность, не качество решения. Поле получает вес целиком либо 0.
Пустые строки, только пробелы/пунктуация и известные заглушки (`не знаю`, `неизвестно`,
`пока неизвестно`, `не определено`, `не указано`, `нет информации`, `нет данных`,
`уточняется`, `будет позже`, `позже`, `TBD`, `TODO`, `unknown`, `N/A`, `NA`, `none`,
`null`, `нет`, `no`) баллов не дают, без учёта регистра и краевой пунктуации.
Значимые ограничения вроде «Без платных сервисов» считаются заполнением.
Это прозрачная эвристика: произвольный бессмысленный текст семантически не проверяется.

| Ключ компонента | Вес |
| --- | --- |
| context_need | context 10 + need 10 = 20 |
| data_materials | 20 |
| expected_result | 15 |
| success_criteria | 15 |
| constraints | 10 |
| users | 10 |
| contact_interaction | contact 5 + interaction_format 5 = 10 |

0–39 draft; 40–69 workable; 70–89 ready; 90–100 priority.
Title и topic баллов не дают; description не оценивается отдельно от карточки.
Missing fields включает все незаполненные поля карточки, в том числе title;
recommendations содержит соответствующие вопросы-подсказки.

Низкий рейтинг, включая 0, НЕ запрещает публикацию и НЕ запрещает отклик.

## Каталог

Только published. Сортировка: rating_desc (по умолчанию), rating_asc или newest;
при равенстве — id DESC. Фильтры topic (точное совпадение после trim/casefold)
и level (draft/workable/ready/priority) объединяются через AND. Topic задаётся
пользователем, AI её не придумывает. Limit/offset применяются после фильтрации.

## AI: содержательная функция и защита от выдуманных фактов

Единая функция `TaskAI.prepare` выполняет извлечение и классификацию исходных
сведений по полям карточки, определяет приоритет уточнений и формирует карточку.

- `AI_PROVIDER=mock` по умолчанию: полностью локальная детерминированная реализация.
  Она понимает явные метки `Контекст:`, `Проблема:`, `Данные:`, `Результат:`,
  `Критерии успеха:`, `Пользователи:`, `Ограничения:`, `Контакт:`,
  `Формат взаимодействия:`, `Название:` и английские имена полей.
  Разделители — новая строка, точка с пробелом, точка с запятой.
  Свободный текст без меток сохраняется в context без домыслов.
- `AI_PROVIDER=openai`: OpenAI Responses API, Structured Outputs, JSON Schema.
  Модель определяется OPENAI_MODEL (по умолчанию gpt-4o-mini), ключ OPENAI_API_KEY.
  Запрос только при создании задачи и сохранении ответов, не на GET/PATCH/confirm.
- Внешняя модель возвращает assignments вида field/source_id и question_fields.
  В схеме вообще нет свободного текста, которым можно заполнить карточку.
- Каждое значение берётся сервером из целого фрагмента пользовательского ввода.
  Произвольные значения, несуществующие source_id, дубли, чужие поля и неверные типы
  отклоняются Pydantic и проверкой источников. Отрицания и условия не обрезаются.
- Явно размеченные пользователем поля, ответы и ручные правки сохраняются точно.
  Модель не может переносить их в другие поля, стирать или восстанавливать очищенное.
- Вопросы формируются из безопасных шаблонов выбранных полей: в вопрос нельзя
  внедрить придуманную предпосылку о бюджете, данных или сроках.
- Отсутствие ключа, отказ, неполный ответ, неверный JSON/структура, timeout,
  HTTP 429/5xx и ошибка источников приводят к локальному fallback, не HTTP 500.
- Metadata сообщает mock/openai/fallback/legacy и стабильную причину fallback.
  Текст запросов, ответы модели и ключи не логируются; store=false.
  Таймаут HTTP-операций 12 секунд, автоматических повторов нет.

Источник факта проверяется строго; семантическая классификация полного фрагмента
моделью всё ещё может быть неточной. Поэтому карточка редактируется и требует
ручного подтверждения. Mock — рабочая эвристика для демо, не имитация вызова LLM.

## SQLite и миграция

DATABASE_URL по умолчанию sqlite:///./database/app.db. Относительный путь
разрешается от корня проекта; поддерживается файловая SQLite. `.env` из корня,
переменные процесса имеют приоритет. FK включены, timeout блокировки 10 секунд.

`database/migrate.py` выполняет идемпотентное транзакционное обновление v1 → v2
при старте/seed или явно. Добавляет колонки без удаления таблиц; старый message
копируется в solution_idea, недостающие plan/duration/URL остаются пустыми.
Темы старых записей остаются пустыми; существующие факты не дополняются догадками.
Пересчитывает старые рейтинги без изменения updated_at. Версия — PRAGMA user_version=2.
Перед обновлением рабочей базы в этой сессии сделана копия database/app.pre-v2.db.

Seed содержит 8 задач, 5 профилей команд и 5 предложений; повторный запуск пропускает существующие
записи без перезаписи правок. Новые v2-примеры: аналитика/70, автоматизация/100,
образование/0. Старое accepted-предложение — заранее заданное состояние фикстуры,
не результат автоматического выбора алгоритмом.

## Границы MVP

Авторизации, проверки владельцев и загрузки файлов нет. Контакты доступны через API.
Для демо предполагается один процесс и последовательное редактирование карточек.
Нет оптимистической блокировки карточек, поиска по тексту, переоткрытия решений,
антиспама или дедупликации команд. Демо-роли переключаются в интерфейсе.

Реализация внешнего адаптера опирается на
[официальную документацию Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)
и [Responses API](https://developers.openai.com/api/docs/guides/migrate-to-responses).
